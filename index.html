02 Java là pass-by-value hay pass-by-reference? 🟢 Junior ▾

Java luôn luôn là pass-by-value. Tuy nhiên với object, giá trị được pass là bản sao của reference (địa chỉ), không phải object gốc.

void change(StringBuilder sb) { sb.append(" World"); // OK - thay đổi object gốc qua reference sb = new StringBuilder(); // KHÔNG ảnh hưởng caller - reassign local copy } StringBuilder s = new StringBuilder("Hello"); change(s); System.out.println(s); // "Hello World" - append có, nhưng reassign không
💡 Cách nhớ: bạn truyền vào địa chỉ nhà (copy), người nhận có thể vào nhà sửa đồ đạc, nhưng không thể thay đổi địa chỉ trong danh bạ của bạn.
03 4 tính chất OOP trong Java? 🔘 Intern ▾
  • Encapsulation (Đóng gói): Che giấu data bên trong class, chỉ expose qua getter/setter. Tăng bảo mật, kiểm soát truy cập.
  • Inheritance (Kế thừa): Class con kế thừa field/method của class cha. Tái sử dụng code. Java chỉ hỗ trợ đơn kế thừa (extends).
  • Polymorphism (Đa hình): Cùng một method nhưng hành vi khác nhau tuỳ object. Có 2 loại: compile-time (overloading) và runtime (overriding).
  • Abstraction (Trừu tượng): Ẩn chi tiết implement, chỉ show interface. Dùng abstract class hoặc interface.

05 == vs .equals() khác nhau thế nào? 🔘 Intern ▾

== so sánh địa chỉ bộ nhớ (reference). .equals() so sánh nội dung giá trị (nếu được override).

String a = new String("hello"); String b = new String("hello"); System.out.println(a == b); // false - khác địa chỉ System.out.println(a.equals(b)); // true - cùng nội dung String c = "hello"; String d = "hello"; System.out.println(c == d); // true - cùng String Pool
⚠️ Với Integer: Integer a = 127; Integer b = 127; a == b là true (Integer cache -128 đến 127). Nhưng Integer a = 200; Integer b = 200; a == b là false!

08 static keyword dùng để làm gì? 🔘 Intern ▾

10 Constructor có thể được override không? 🔘 Intern ▾

Không thể override constructor. Constructor không được kế thừa — subclass không kế thừa constructor của superclass, nên không có gì để override.

Tuy nhiên, constructor có thể overload (nhiều constructor khác tham số trong cùng 1 class).

Subclass có thể gọi constructor cha bằng super() — nhưng đó là gọi, không phải override.

class Animal { Animal(String name) { ... } } class Dog extends Animal { Dog(String name) { super(name); // gọi constructor cha, không phải override } }

12 HashMap hoạt động như thế nào? 🔵 Middle ▾

HashMap dùng hashing: khi put(key, value), Java tính hash(key) → xác định vị trí (bucket index) trong mảng nội bộ.

  • Collision: Nếu 2 key có cùng bucket → lưu thành chain (LinkedList). Từ Java 8, nếu chain dài ≥ 8 → chuyển sang TreeNode (O(log n)).
  • Load factor: Mặc định 0.75. Khi fill > 75% capacity → resize (double size, rehash tất cả).
  • Độ phức tạp: get/put trung bình O(1), tệ nhất O(log n).
// Khi put("name", "John"): 1. hash = "name".hashCode() // → tính hash 2. index = hash & (capacity - 1) // → tìm bucket 3. Nếu bucket trống → lưu vào 4. Nếu đã có key giống → update value 5. Nếu collision → thêm vào chain
⚠️ HashMap không đảm bảo thứ tự. Dùng LinkedHashMap nếu cần giữ insertion order, TreeMap nếu cần sorted order.

14 HashMap vs ConcurrentHashMap khác nhau thế nào? 🔵 Middle ▾

ConcurrentHashMap thread-safe nhưng hiệu năng tốt hơn HashTable vì không lock toàn bộ map.

  • Java 7: chia thành nhiều Segment, mỗi segment có lock riêng → nhiều thread read/write song song trên segment khác nhau.
  • Java 8+: dùng CAS (Compare-And-Swap) + synchronized chỉ trên từng bucket khi cần — ít blocking hơn nhiều.
  • Không cho phép null key/value (HashMap cho phép 1 null key).
💡 Rule of thumb: single-thread → HashMap; multi-thread → ConcurrentHashMap.
15 HashSet hoạt động như thế nào? 🟢 Junior ▾

HashSet thực chất là HashMap bên trong: element được lưu làm key, value là một dummy object PRESENT.

Tính duy nhất đảm bảo bởi: hashCode() + equals(). Nếu 2 object có cùng hashCode VÀ equals trả về true → được coi là trùng → không thêm vào.

// Khi add("hello"): map.put("hello", PRESENT); // PRESENT = new Object() // Nếu "hello" đã tồn tại → put chỉ update value (PRESENT lại) // → HashSet báo là đã có, không thêm
⚠️ Phải override cả hashCode() và equals() nếu dùng custom object trong HashSet/HashMap!
16 equals() và hashCode() contract là gì? 🔵 Middle ▾

Java quy định contract bắt buộc:

  • Nếu a.equals(b) == true → a.hashCode() == b.hashCode() BẮT BUỘC
  • Nếu a.hashCode() == b.hashCode() → chưa chắc a.equals(b) (collision bình thường)
⚠️ Vi phạm contract này khiến HashMap/HashSet hoạt động sai: 2 object "bằng nhau" nhưng lại nằm ở 2 bucket khác nhau → tìm không ra.
// Ví dụ SAI - chỉ override equals, quên hashCode class User { String name; @Override boolean equals(Object o) { return name.equals(((User)o).name); } // ❌ không override hashCode → HashMap hoạt động sai! }

20 fail-fast vs fail-safe iterator là gì? 🔵 Middle ▾
  • fail-fast: Ném ConcurrentModificationException ngay lập tức nếu collection bị sửa đổi trong khi đang duyệt. Dùng biến modCount để phát hiện. Ví dụ: ArrayList, HashMap iterator.
  • fail-safe: Duyệt trên bản sao (snapshot) của collection → không ảnh hưởng bởi thay đổi. Không throw exception nhưng có thể không phản ánh thay đổi mới nhất. Ví dụ: CopyOnWriteArrayList, ConcurrentHashMap.
// fail-fast - sẽ throw ConcurrentModificationException List<String> list = new ArrayList<>(Arrays.asList("a","b","c")); for (String s : list) { if (s.equals("b")) list.remove(s); // ❌ Exception! } // Cách đúng: dùng iterator.remove() Iterator<String> it = list.iterator(); while (it.hasNext()) { if (it.next().equals("b")) it.remove(); // ✅ OK }

22 Error vs Exception khác nhau thế nào? 🟢 Junior ▾

Cả hai đều extends Throwable, nhưng:

  • Error: Lỗi nghiêm trọng từ JVM/system, thường không thể recover. Ví dụ: OutOfMemoryError, StackOverflowError. Không nên catch (và thường không thể handle được).

23 try-with-resources là gì? 🔵 Middle ▾

Cú pháp Java 7+ tự động gọi close() trên resource sau khi dùng xong, dù có exception hay không. Resource phải implement AutoCloseable.

24 finally block có luôn chạy không? 🟢 Junior ▾

  • System.exit() được gọi trong try/catch
  • JVM crash (OutOfMemoryError, kill process)

27 synchronized keyword dùng để làm gì? 🔵 Middle ▾

synchronized đảm bảo chỉ 1 thread được vào block/method tại một thời điểm, tránh race condition. Thread khác phải chờ (blocked).

  • synchronized method: Lock trên this (instance)
  • static synchronized method: Lock trên Class object
  • synchronized block: Lock trên object chỉ định, phạm vi hẹp hơn → ít blocking hơn
// synchronized method public synchronized void increment() { count++; } // synchronized block - tốt hơn vì chỉ lock khi cần public void increment() { doSomethingWithoutLock(); // Không cần lock - chạy song song synchronized (this) { count++; // Chỉ lock phần cần thiết } }
28 volatile keyword dùng để làm gì? 🔵 Middle ▾

volatile đảm bảo biến được đọc/ghi trực tiếp từ main memory, không bị cache trong CPU register của từng thread.

Giải quyết visibility problem: Thread A thay đổi biến nhưng Thread B vẫn thấy giá trị cũ từ cache.

class StopThread { private volatile boolean running = true; // không có volatile, thread có thể không thấy thay đổi void run() { while (running) { doWork(); } // đọc từ main memory mỗi lần } void stop() { running = false; } // ghi vào main memory ngay }
⚠️ volatile KHÔNG đảm bảo atomicity! count++ gồm 3 bước (read, increment, write) — vẫn cần synchronized hoặc AtomicInteger.
29 wait(), notify(), notifyAll() dùng để làm gì? 🔵 Middle ▾

Dùng trong synchronized block để điều phối các thread chờ nhau (Producer-Consumer pattern):

  • wait(): Thread giải phóng lock và đi ngủ, chờ được đánh thức
  • notify(): Đánh thức 1 thread ngẫu nhiên đang wait trên cùng object
  • notifyAll(): Đánh thức tất cả thread đang wait → các thread cạnh tranh lại lock
// Producer-Consumer đơn giản synchronized (queue) { while (queue.isEmpty()) { queue.wait(); // giải phóng lock, chờ có data } process(queue.poll()); } // Khi Producer thêm data: synchronized (queue) { queue.add(item); queue.notifyAll(); // đánh thức consumer }
💡 Thực tế dùng BlockingQueue (LinkedBlockingQueue, ArrayBlockingQueue) thay vì tự implement — đơn giản và an toàn hơn.
30 Deadlock là gì? Cách tránh? 🔵 Middle ▾

Deadlock xảy ra khi 2+ thread chờ nhau giải phóng lock vô thời hạn.

// Thread 1: lock A → chờ B // Thread 2: lock B → chờ A → DEADLOCK!

Cách tránh Deadlock:

  • ✅ Thứ tự lock nhất quán: Luôn lock A trước B, không bao giờ ngược lại
  • ✅ tryLock với timeout: lock.tryLock(1, TimeUnit.SECONDS) — nếu không được thì bỏ qua
  • ✅ Giảm phạm vi lock: Chỉ lock khi thực sự cần, release sớm nhất có thể
  • ✅ Dùng concurrent collections: ConcurrentHashMap, BlockingQueue... thay vì tự lock

34 Atomic classes là gì? 🔵 Middle ▾

Các class trong java.util.concurrent.atomic thực hiện thao tác thread-safe không cần synchronized, dùng CAS (Compare-And-Swap) ở CPU level — nhanh hơn synchronized.

// Không thread-safe int count = 0; count++; // 3 bước: read, increment, write → race condition // Thread-safe với AtomicInteger AtomicInteger count = new AtomicInteger(0); count.incrementAndGet(); // atomic, không cần synchronized count.compareAndSet(5, 10); // chỉ set 10 nếu hiện tại là 5

Các class phổ biến: AtomicInteger, AtomicLong, AtomicBoolean, AtomicReference, LongAdder (hiệu năng cao hơn trong high-contention).

42 Garbage Collection hoạt động như thế nào? 🔵 Middle ▾

GC tự động thu hồi object trong Heap không còn được tham chiếu, dùng Generational GC:

Heap ├── Young Generation │ ├── Eden Space ← object mới tạo tại đây │ ├── Survivor S0 ← sống sót sau Minor GC │ └── Survivor S1 ├── Old Generation ← object sống lâu được promote └── Metaspace ← class metadata (Java 8+)
  • Minor GC: Dọn Young Generation, nhanh (~ms). Object sống sót được chuyển sang Survivor.
  • Major/Full GC: Dọn Old Generation, chậm hơn → Stop-The-World pause.
  • Thuật toán: G1GC (default Java 9+), ZGC (Java 15+, pause <1ms), Shenandoah.

141 JIT Compiler là gì? Tại sao JVM khởi động chậm nhưng sau đó nhanh? 🟠 Senior ▾

JIT (Just-In-Time) Compiler biên dịch bytecode thành native machine code tại runtime — chỉ với những method được gọi nhiều lần (hot spots). Đây là lý do Java nhanh sau khi "warm up".

JVM lifecycle: 1. Load .class → bytecode (interpreted mode) ← CHẬM ban đầu 2. JIT phát hiện "hot method" (gọi nhiều lần) 3. JIT compile hot method → native code + cache 4. Lần sau gọi → chạy native code trực tiếp ← NHANH Threshold mặc định: ~10,000 lần gọi = hot method
  • C1 Compiler (Client): Compile nhanh, ít optimize — cho startup nhanh
  • C2 Compiler (Server): Compile chậm hơn nhưng optimize sâu hơn — performance đỉnh
  • Tiered Compilation (default Java 8+): Dùng C1 trước → sau đó C2 cho hot spots
💡 Đây là lý do khi load test Spring Boot app: 5 phút đầu chậm hơn, sau đó "warm up" xong và throughput tăng đáng kể.

79 @Transactional dùng để làm gì? 🔵 Middle ▾

Đánh dấu method/class chạy trong một transaction database. Nếu method thành công → commit. Nếu exception xảy ra → tự động rollback.

Spring implement bằng AOP proxy: tạo proxy bao bọc method, quản lý transaction xung quanh lời gọi thật.

@Transactional public void transfer(Long fromId, Long toId, double amount) { Account from = accountRepo.findById(fromId).orElseThrow(); Account to = accountRepo.findById(toId).orElseThrow(); from.deduct(amount); // nếu exception ở đây to.deposit(amount); // cả 2 đều rollback → tài khoản không mất tiền }
⚠️ Gọi @Transactional method từ cùng class (self-invocation) không hoạt động vì Spring AOP dùng proxy — lời gọi nội bộ bypass proxy. Fix: inject bean vào chính nó hoặc dùng AspectJ weaving.

84 Authentication vs Authorization khác nhau thế nào? 🔵 Middle ▾
  • Authentication (Xác thực): "Bạn là ai?" — Xác minh danh tính. Ví dụ: kiểm tra username/password, validate JWT token.
  • Authorization (Phân quyền): "Bạn được làm gì?" — Kiểm tra quyền truy cập sau khi đã xác thực. Ví dụ: chỉ ADMIN mới xoá được user.

85 JWT là gì? Dùng trong Spring Security thế nào? 🔵 Middle ▾

JWT (JSON Web Token) là token tự chứa thông tin, gồm 3 phần phân cách bằng dấu chấm: header.payload.signature

eyJhbGciOiJIUzI1NiJ9 ← header (algorithm) .eyJ1c2VySWQiOjEsInJvbGUiOiJVU0VSIn0 ← payload (claims: userId, role...) .HMACSHA256(...) ← signature (verify không bị tampered)

Luồng JWT trong Spring Security:

  • Login → server tạo JWT, ký bằng secret key → trả về client
  • Client gửi request kèm Authorization: Bearer <token>
  • JwtFilter intercept → verify chữ ký → extract user info → set vào SecurityContext
  • Controller nhận request đã được authenticate
💡 Ưu điểm JWT: Stateless — server không cần lưu session. Nhược điểm: không thể revoke ngay lập tức. Solution: dùng short expiry + refresh token, hoặc lưu blacklist Redis.

103 Spring AOP là gì? Các khái niệm cơ bản? 🟠 Senior ▾

AOP (Aspect-Oriented Programming): Tách cross-cutting concern (logging, security, transaction, audit...) ra khỏi business logic.

Các khái niệm:

  • Aspect: Class chứa cross-cutting logic (annotated @Aspect)
  • Advice: Hành động thực hiện — @Before, @After, @AfterReturning, @AfterThrowing, @Around
  • Pointcut: Biểu thức xác định where advice áp dụng (method nào, class nào)
  • Join Point: Điểm cụ thể trong execution (method call)
@Aspect @Component public class LoggingAspect { @Around("execution(* com.example.service.*.*(..))") public Object logExecutionTime(ProceedingJoinPoint pjp) throws Throwable { long start = System.currentTimeMillis(); Object result = pjp.proceed(); // gọi method gốc long time = System.currentTimeMillis() - start; log.info("{} executed in {}ms", pjp.getSignature(), time); return result; } }

111 Kafka là gì? Tại sao dùng Kafka? 🟢 Junior ▾

Apache Kafka là distributed event streaming platform — hệ thống message broker phân tán, hiệu năng cao, dùng để truyền dữ liệu giữa các service theo mô hình publish/subscribe.

Tại sao dùng Kafka?

  • Tách coupling: Producer không cần biết Consumer — service A gửi event, service B/C/D xử lý độc lập
  • Throughput cao: Ghi hàng triệu message/giây nhờ sequential disk I/O (append-only log)
  • Replay được: Message lưu trên disk (mặc định 7 ngày), Consumer có thể đọc lại từ đầu
  • Fault-tolerant: Replication — dữ liệu được sao chép sang nhiều broker
  • Scalable: Thêm partition, thêm consumer dễ dàng
💡 Ví dụ thực tế: Đặt hàng → Kafka → Order Service, Inventory Service, Notification Service xử lý song song — không cần gọi trực tiếp nhau.
112 Topic, Partition, Offset, Consumer Group trong Kafka là gì? 🔵 Middle ▾
  • Topic: Kênh dữ liệu — giống như một "hàng đợi có tên". VD: order-created, payment-processed
  • Partition: Topic được chia thành nhiều partition — đơn vị song song hóa. Mỗi partition là một append-only log, được ghi tuần tự.
  • Offset: Số thứ tự của message trong partition (bắt đầu từ 0). Consumer lưu offset để biết đã đọc đến đâu.
  • Consumer Group: Nhóm consumer cùng nhau xử lý một topic. Mỗi partition chỉ được đọc bởi 1 consumer trong group tại một thời điểm → load balancing tự động.
Topic: order-created (3 partitions) ├── Partition 0: [msg0, msg1, msg4, ...] ← Consumer 1 đọc ├── Partition 1: [msg2, msg5, ...] ← Consumer 2 đọc └── Partition 2: [msg3, msg6, ...] ← Consumer 3 đọc Consumer Group A: 3 consumers → mỗi consumer 1 partition Consumer Group B: 1 consumer → consumer đó đọc cả 3 partition
⚠️ Số consumer trong group > số partition → consumer thừa sẽ idle (không nhận message).

129 ACID là gì? Giải thích từng thuộc tính? 🔵 Middle ▾

ACID là 4 thuộc tính đảm bảo độ tin cậy của database transaction:

  • 🔵 Atomicity (Nguyên tử): Toàn bộ transaction thành công hoặc toàn bộ thất bại — không có "nửa vời". VD: chuyển tiền phải trừ A VÀ cộng B, không được chỉ trừ A.
  • 🟢 Consistency (Nhất quán): DB luôn ở trạng thái hợp lệ trước và sau transaction. VD: tổng tiền trong hệ thống phải không đổi sau khi chuyển.
  • 🟡 Isolation (Cô lập): Transaction đang chạy không bị ảnh hưởng bởi transaction khác chạy song song.
  • 🔴 Durability (Bền vững): Sau khi commit thành công, data được persist dù server crash. DB ghi vào disk/WAL log.
💡 NoSQL thường trade-off ACID lấy performance/scalability. Theo CAP theorem: không thể có cả Consistency, Availability, Partition tolerance — phải chọn 2.

Nên tạo index:

  • Column thường dùng trong WHERE, JOIN, ORDER BY
  • Foreign key columns
  • Column có cardinality cao (nhiều giá trị khác nhau)

  • Bảng nhỏ (full scan nhanh hơn)
  • Column ít distinct values (VD: gender — chỉ 2 giá trị)
  • Column thường xuyên bị UPDATE (index phải rebuild sau mỗi write)

Sharding là kỹ thuật chia data nằm ngang (horizontal partitioning) ra nhiều DB server độc lập, mỗi server giữ một phần data.

VD: Bảng users 100 triệu record chia thành 4 shard: Shard 1: user_id % 4 == 0 → DB Server 1 (0-25M) Shard 2: user_id % 4 == 1 → DB Server 2 Shard 3: user_id % 4 == 2 → DB Server 3 Shard 4: user_id % 4 == 3 → DB Server 4

Vấn đề khi Sharding:

  • ❌ Transaction cross-shard khó đảm bảo ACID
  • ❌ Rebalancing khi thêm shard tốn kém
⚠️ Chỉ dùng sharding khi thực sự cần (hàng chục triệu record, single DB không đủ). Trước tiên thử: indexing, caching, read replica, connection pooling.

146 Two-Phase Commit (2PC) là gì? Tại sao ít dùng trong microservice? 🟣 Expert ▾

2PC là giao thức đảm bảo distributed transaction — tất cả participants commit hoặc tất cả rollback:

Phase 1 - Prepare: Coordinator → tất cả participants: "Bạn có sẵn sàng commit không?" Participants ghi redo log, trả lời "YES" hoặc "NO" Phase 2 - Commit/Abort: Nếu TẤT CẢ trả YES → Coordinator gửi COMMIT Nếu BẤT KỲ trả NO → Coordinator gửi ROLLBACK

Vấn đề của 2PC trong Microservice:

  • ❌ Blocking: Participants lock resource trong suốt quá trình → giảm throughput
  • ❌ Single point of failure: Coordinator chết → participants bị block mãi
  • ❌ Latency cao: Nhiều round-trip network
  • ❌ Tight coupling: Tất cả services phải support 2PC protocol
💡 Thay bằng Saga Pattern (eventual consistency) — chấp nhận eventual consistency thay vì strong consistency. Phù hợp hơn với microservice.

Index Scan on users ← ✅ Dùng index tốt cost=0.00..1234.56 ← Ước tính cost (nhỏ hơn = tốt hơn) rows=5000 ← Số rows ước tính actual time=123.456ms ← Thời gian thực tế Buffers: hit=100 read=500 ← read nhiều = cache miss, chậm

  • Seq Scan trên bảng lớn → thiếu index
  • Hash Join với rows lớn → cân nhắc index trên JOIN column

HikariCP là connection pool nhanh nhất cho Java (default trong Spring Boot). Thay vì mở/đóng DB connection mỗi request (tốn ~100ms) → giữ sẵn pool connection để tái sử dụng.

# Formula của HikariCP team: pool_size = (core_count * 2) + effective_spindle_count # Ví dụ: server 4 CPU, SSD (spindle=0): pool_size = (4 * 2) + 1 = 9 → ~10

163 Clean Architecture là gì? Tại sao business logic không nên phụ thuộc framework? 🟣 Expert ▾

Clean Architecture (Uncle Bob) tổ chức code theo vòng tròn đồng tâm — dependency chỉ hướng vào trong, core business không biết gì về framework/DB/UI.

Ngoài → Trong (dependency direction): ┌──────────────────────────────────┐ │ Frameworks & Drivers │ Spring, Hibernate, REST │ ┌────────────────────────────┐ │ │ │ Interface Adapters │ │ Controller, Repository impl │ │ ┌──────────────────────┐ │ │ │ │ │ Application Layer │ │ │ Use Cases / Services │ │ │ ┌────────────────┐ │ │ │ │ │ │ │ Domain Layer │ │ │ │ Entities, Business Rules │ │ │ │ (Không phụ │ │ │ │ ← KHÔNG import Spring! │ │ │ │ thuộc gì) │ │ │ │ │ │ │ └────────────────┘ │ │ │ │ │ └──────────────────────┘ │ │ │ └────────────────────────────┘ │ └──────────────────────────────────┘

Lợi ích:

  • ✅ Đổi từ REST sang GraphQL → chỉ thay Controller, không động đến business logic
  • ✅ Đổi từ MySQL sang MongoDB → chỉ thay Repository impl
  • ✅ Test business logic thuần Java — không cần Spring context, test siêu nhanh

166 Design Rate Limiter — các thuật toán và implement ở scale? 🟣 Expert ▾

Yêu cầu: Giới hạn mỗi user tối đa 100 request/phút. Scale: 100M users, 10M req/s.

Thuật toán — Sliding Window Log (Redis Sorted Set):

Key: "rate:{userId}" Type: Sorted Set Score: timestamp MULTI # atomic transaction ZREMRANGEBYSCORE rate:user1 0 (now-60s) # xóa request cũ ZADD rate:user1 now {uuid} # thêm request hiện tại ZCARD rate:user1 # đếm trong 60s EXEC if count > 100: return 429 Too Many Requests

Scale lên 10M req/s:

  • 🔴 Redis Cluster: Shard theo userId để phân tải
  • 🌐 API Gateway level: Implement tại gateway (Kong, AWS API GW) — không cần đến service
  • 💾 Local cache: Mỗi instance cache quota ngắn hạn, sync với Redis định kỳ (token bucket)
  • ⚡ Lua script: Atomic operation trong Redis để tránh race condition
